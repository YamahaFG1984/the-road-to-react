这一章做两件事。第一，把数据请求逻辑从 effect 里提取成一个函数，借此认识 useCallback —— 以及如果不用它，为什么会陷入无限循环。第二，解决“每敲一个键就请求一次”的问题：改为点击按钮才搜索。

本章目标

  • 理解“每次渲染都会创建新函数”对 effect 依赖的影响
  • 用 useCallback 记忆化函数，看懂依赖链
  • 把“输入中的搜索词”和“确认后的请求地址”拆成两个状态，实现显式获取
  • 了解 React Compiler 对 useCallback 的影响

把请求逻辑提取出来

先做一个看起来很普通的重构：把 effect 里的请求代码搬到一个独立的函数 handleFetchStories 里（A）， 用 useCallback 包起来（B），然后在 effect 里调用它（C）：

```jsx src/App.jsx import { useState, useEffect, useRef, useReducer, useCallback } from 'react'; const App = () => { ... // A const handleFetchStories = useCallback(() => { // B if (!searchTerm) return; dispatchStories({ type: 'STORIES_FETCH_INIT' }); fetch(`${API_ENDPOINT}${searchTerm}`) .then((response) => response.json()) .then((result) => { dispatchStories({ type: 'STORIES_FETCH_SUCCESS', payload: result.hits, }); }) .catch(() => dispatchStories({ type: 'STORIES_FETCH_FAILURE' }) ); }, [searchTerm]); // E useEffect(() => { handleFetchStories(); // C }, [handleFetchStories]); // D ... }; ```

应用的行为没有变化。好处是请求逻辑变成了一个可以在别处调用的函数（虽然暂时还没用上）。 关键在于那个 useCallback —— 它为什么是必须的？

不用 useCallback 会怎样

第 3 章说过：组件每次渲染，函数体从头执行，里面定义的函数也都是全新的。 两次渲染中的 handleFetchStories 虽然代码一样，却是两个不同的函数对象（fn1 !== fn2）。 而 effect 依赖了它（D），于是：

useCallback：记住一个函数

useCallback(fn, deps) 让 React 在多次渲染之间返回同一个函数对象，只有当依赖数组（E）里的值变化时，才换成新创建的函数。 这样依赖链就变成了：

ⓘ 更简单的替代写法

如果请求函数只在 effect 里用，最简单的办法是把函数定义在 effect 内部， 这样它就不是依赖，也就不需要 useCallback。只有当函数需要在 effect 之外复用（比如“刷新”按钮也要调用它）时，才需要本章的写法。

显式获取：点按钮才搜索

回到限流问题：现在每次输入都会发请求。改成用户点 “Submit” 按钮时才请求。

💡 先自己试试

提示：加一个按钮；新增一个状态表示“已确认的搜索”；按钮的处理函数用当前搜索词设置这个状态； 只有这个新状态变化时才执行请求。

关键点是要有两个状态：一个随输入不断变化的 searchTerm，一个只在确认时才变的 url。先加按钮：

```jsx src/App.jsx const App = () => { ... return (

My Hacker Stories

Search: ...
); }; ```

输入框的处理函数改名为 handleSearchInput，照旧更新 searchTerm；按钮的处理函数用它拼出 url：

```jsx src/App.jsx const App = () => { const [searchTerm, setSearchTerm] = useStorageState('search', 'React'); const [url, setUrl] = useState(`${API_ENDPOINT}${searchTerm}`); ... const handleSearchInput = (event) => { setSearchTerm(event.target.value); }; const handleSearchSubmit = () => { setUrl(`${API_ENDPOINT}${searchTerm}`); }; ... }; ```

最后，请求函数改为依赖 url 而不是 searchTerm：

```jsx src/App.jsx const handleFetchStories = useCallback(() => { dispatchStories({ type: 'STORIES_FETCH_INIT' }); fetch(url) .then((response) => response.json()) .then((result) => { dispatchStories({ type: 'STORIES_FETCH_SUCCESS', payload: result.hits, }); }) .catch(() => dispatchStories({ type: 'STORIES_FETCH_FAILURE' }) ); }, [url]); useEffect(() => { handleFetchStories(); }, [handleFetchStories]); ```

现在输入时只更新输入框；点击 Submit 才会请求。按钮在搜索词为空时是禁用的（disabled={!searchTerm}）， 所以请求函数里也不需要再检查空字符串了。

ⓘ 为什么 url 用 useState 而不是 useStorageState？

url 完全由常量 API_ENDPOINT 和 searchTerm 拼成，而 searchTerm 已经存进了 localStorage， 初始 url 可以从它推出来，没必要再存一份。

新旧对照：React Compiler 与 useCallback

在 React 19 时代，React Compiler（2025 年 10 月发布 1.0）可以在构建时自动分析组件， 给需要的函数和值加上记忆化 —— 效果相当于自动帮你写 useCallback 和 useMemo：

手动记忆化 无编译器
```jsx const handleFetchStories = useCallback(() => { fetch(url)... }, [url]); useEffect(() => { handleFetchStories(); }, [handleFetchStories]); ```
启用 React Compiler React 19
```jsx // 编译器会自动让这个函数在 url 不变时保持同一引用 const handleFetchStories = () => { fetch(url)... }; useEffect(() => { handleFetchStories(); }, [handleFetchStories]); ```

不过要注意两点：第一，编译器需要额外配置（第 28 章），默认的 Vite 模板没有开启； 第二，useCallback 并没有被废弃，理解它“为什么需要”才能看懂大量现有代码。 本教程在没有编译器的前提下继续手动使用它。

小结

  • 每次渲染都会创建新的函数对象；把这样的函数作为 effect 依赖会导致 effect 每次都执行，甚至无限循环。
  • useCallback(fn, deps) 在依赖不变时返回同一个函数，依赖链：状态 → 函数 → effect。
  • 函数只在 effect 内使用时，直接定义在 effect 里面更简单。
  • 显式获取：searchTerm 管输入，url 管请求，点击按钮时用前者设置后者。
  • React Compiler 可以自动完成记忆化，但需要单独启用。

动手练习

  1. （小心，浏览器可能卡住）去掉 useCallback，观察 Network 面板里的请求；然后马上改回来。
  2. 把请求函数改写为定义在 effect 内部的版本，确认不再需要 useCallback。
  3. 加一个 “Refresh” 按钮，点击时直接调用 handleFetchStories() 重新请求当前结果 —— 这正是把函数提取到 effect 外面的意义。

面试题

useCallback 的作用是什么？

在依赖不变时，跨渲染返回同一个函数引用，避免因函数“身份”变化而导致的 effect 重复执行或子组件无谓的重新渲染。

useCallback 的参数是什么？依赖为空数组时会怎样？

第一个参数是要记忆化的函数，第二个是依赖数组；空数组表示函数只在首次渲染时创建，之后一直不变（注意它读到的状态也会停留在首次渲染时）。

为什么把普通函数作为 useEffect 依赖可能导致无限循环？

每次渲染都创建新函数，effect 认为依赖变化而执行；若 effect 内更新了状态，就会引发新的渲染，循环往复。

为什么 url 状态用 useState 而不是 useStorageState？

url 由常量和已持久化的 searchTerm 派生，不需要再单独持久化。

React Compiler 会让 useCallback 过时吗？

启用编译器后大多数手动记忆化可以省略，但 useCallback 仍是有效 API，在未启用编译器的项目和需要精确控制的场景中依然使用。
