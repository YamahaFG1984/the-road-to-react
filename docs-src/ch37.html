推荐模式：Provider 组件 + 自定义 Hook

不要把 createContext 散落在各处使用。把 Context、状态逻辑和读取方式封装在一个文件里：

    主题切换

    主题是 Context 最经典的用例：值很少变化，却几乎每个组件都可能用到。

    ```jsx src/theme.jsx import { createContext, use, useEffect } from 'react'; const ThemeContext = createContext(null); const ThemeProvider = ({ children }) => { const [theme, setTheme] = useStorageState('theme', 'light'); // 第 15 章的 Hook useEffect(() => { // 同步到 ，CSS 根据它切换颜色变量 document.documentElement.dataset.theme = theme; }, [theme]); const toggleTheme = () => setTheme((current) => (current === 'light' ? 'dark' : 'light')); return ( {children} ); }; const useTheme = () => { const context = use(ThemeContext); if (!context) throw new Error('useTheme must be used within a ThemeProvider'); return context; }; export { ThemeProvider, useTheme }; ``` ```css src/index.css :root { --bg: #ffffff; --fg: #171212; } [data-theme='dark'] { --bg: #171212; --fg: #f5f5f5; } body { background: var(--bg); color: var(--fg); } ```

    注意这里的分工：React 只负责“当前是哪个主题”这一个状态，颜色的切换交给 CSS 变量完成。 这样主题变化时，大部分组件根本不需要重新渲染 —— 它们的样式由浏览器自动更新。

    Context 的代价：重新渲染

    Context 的值一变，所有读取这个 Context 的组件都会重新渲染，即使它们只用到了值的一小部分。 而且注意上面 Provider 里的 value={{ favorites, dispatch }}：每次 Provider 渲染都会创建一个新对象， 消费者会认为值变了。

    几个常用的优化手段：

    • 按关注点拆分：主题、收藏、用户各一个 Context，互不影响。
    • 稳定 value：用 useMemo 包住 value 对象（启用 React Compiler 时会自动处理）。
    • 拆分“读”和“写”：dispatch 永远不变，可以放进单独的 Context。只负责触发操作的组件（比如一个“清空收藏”按钮）读取 dispatch Context，就不会因为收藏列表变化而重新渲染。
    • 把变化频繁的状态放在别处：如果一个值每秒变很多次（鼠标位置、输入框内容），不要放进 Context。
    ```jsx const FavoritesProvider = ({ children }) => { const [favorites, dispatch] = useReducer(favoritesReducer, undefined, loadFavorites); // 没有启用 React Compiler 时，手动稳定 value const value = useMemo(() => ({ favorites, dispatch }), [favorites]); return {children}; }; ```

    什么时候用 Context

    场景推荐做法
    只隔了一两层直接传 props，清晰又简单
    中间组件只是“摆放”子组件组件组合：把子组件作为 children 传进去（第 16 章）
    主题、语言、当前登录用户Context：变化少、用的地方多
    搜索词、筛选条件、分页URL（第 36 章）
    从服务器获取的数据TanStack Query 等服务端状态库（第 40 章），它自带共享和缓存
    复杂、频繁更新的全局客户端状态Zustand、Redux Toolkit 等状态管理库（第 45 章）
    ⓘ Context 不是状态管理工具

    Context 本身只是一个“传递机制”：它把一个值从上层送到下层，不负责存储和更新。 真正存状态的仍然是 Provider 里的 useState / useReducer。 理解这一点，就明白为什么大型应用会引入专门的状态管理库：它们在“存储”和“精确订阅”上做得更好。

    新旧对照

    React 18 及以前 旧写法
    ```jsx import { createContext, useContext } from 'react'; {children} const context = useContext(FavoritesContext); // 类组件时代还有 {(v) => …} ```
    React 19 新写法
    ```jsx import { createContext, use } from 'react'; {children} const context = use(FavoritesContext); // use() 还可以在 if 里调用 ```

    小结

    • Context 解决“同一份数据要穿过很多层组件”的问题。
    • 推荐封装：一个文件里包含 Context（不导出）、Provider 组件、自定义 Hook（带 Provider 检查和业务方法）。
    • Context 值变化会让所有消费者重新渲染：按关注点拆分、稳定 value、拆分读写。
    • 不是所有共享状态都适合 Context：URL、服务端状态库、状态管理库各有更合适的场景。

    面试题

    Context 会带来什么性能问题？如何缓解？

    Provider 的 value 变化时所有消费者都会重新渲染。可以拆分 Context、用 useMemo 稳定 value、分离 state 与 dispatch，并避免把高频变化的值放进 Context。

    为什么要为 Context 封装一个自定义 Hook？

    隐藏实现细节、提供统一的业务方法、在 Provider 缺失时给出清晰的错误，以及方便日后替换实现。

    Context 是状态管理方案吗？

    它是依赖注入 / 数据传递机制，状态仍由 useState 或 useReducer 管理；它没有选择性订阅能力，大型应用常配合或改用专门的状态管理库。

    什么情况下不该用 Context？

    只隔一两层（直接传 props）、可以用组件组合解决、数据应该放在 URL 中、属于服务端数据、或更新非常频繁时。
