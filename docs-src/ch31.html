单元测试证明每块积木都没问题，但积木拼在一起还能不能用？这一章测试整个 App： 它会请求数据、显示加载状态、删除文章、执行搜索。我们要解决的第一个问题是 —— 测试里不能真的去请求 Hacker News。 最后再介绍一种轻量的测试方式：快照测试。

本章目标

  • 用 vi.mock 替换 axios，控制网络请求返回什么
  • 用 waitFor 等待异步更新，测试加载、成功、失败三种路径
  • 模拟完整的用户操作：删除、输入、提交搜索
  • 编写快照测试，了解 MSW 等更现代的网络 mock 方式

mock 掉网络请求

App 渲染后会用 axios 请求远程 API。测试里真的发请求既慢又不稳定（网络可能断、数据会变）。 用 Vitest 把整个 axios 模块替换成假的：

```jsx src/App.test.jsx import { describe, it, expect, vi } from 'vitest'; import { render, screen, fireEvent, waitFor } from '@testing-library/react'; import axios from 'axios'; ... vi.mock('axios'); ```

测试数据获取成功

准备一个会兑现的 Promise，让 axios.get 下一次被调用时返回它，然后渲染 App：

```jsx src/App.test.jsx describe('App', () => { it('succeeds fetching data', async () => { const promise = Promise.resolve({ data: { hits: stories, }, }); axios.get.mockImplementationOnce(() => promise); render(); expect(screen.queryByText(/Loading/)).toBeInTheDocument(); await waitFor(async () => await promise); expect(screen.queryByText(/Loading/)).toBeNull(); expect(screen.getByText('React')).toBeInTheDocument(); expect(screen.getByText('Redux')).toBeInTheDocument(); expect(screen.getAllByText('Dismiss').length).toBe(2); }); }); ```
  • waitFor 会反复执行回调，直到它不再抛错（或超时），用来等待异步的状态更新和重新渲染完成。测试函数因此要写成 async。
  • 断言“不存在”用 queryByText：它找不到时返回 null；getByText 找不到会直接抛错。
  • 用正则 /Loading/ 而不是 'Loading'：字符串必须完全匹配 'Loading ...'，正则只要包含即可。
💡 更简洁的等待方式

findBy 系列查询自带等待：expect(await screen.findByText('React')).toBeInTheDocument() 相当于 waitFor + getByText，读起来更直接。

测试数据获取失败

```jsx src/App.test.jsx it('fails fetching data', async () => { const promise = Promise.reject(); axios.get.mockImplementationOnce(() => promise); render(); expect(screen.getByText(/Loading/)).toBeInTheDocument(); try { await waitFor(async () => await promise); } catch (error) { expect(screen.queryByText(/Loading/)).toBeNull(); expect(screen.queryByText(/went wrong/)).toBeInTheDocument(); } }); ```
★ 选择查询函数的经验法则

找单个元素用 getBy，找多个用 getAllBy；要断言元素不存在时用 queryBy / queryAllBy； 要等待元素出现时用 findBy / findAllBy。

测试删除文章

数据加载完成后，点击第一个 Dismiss 按钮，“Jordan Walke” 那条文章应该消失：

```jsx src/App.test.jsx it('removes a story', async () => { const promise = Promise.resolve({ data: { hits: stories, }, }); axios.get.mockImplementationOnce(() => promise); render(); await waitFor(async () => await promise); expect(screen.getAllByText('Dismiss').length).toBe(2); expect(screen.getByText('Jordan Walke')).toBeInTheDocument(); fireEvent.click(screen.getAllByText('Dismiss')[0]); expect(screen.getAllByText('Dismiss').length).toBe(1); expect(screen.queryByText('Jordan Walke')).toBeNull(); }); ```

这次测试的不再是“回调有没有被调用”（第 30 章），而是真实的结果：状态更新了、界面变了。 这就是集成测试的价值 —— Item、List、App 和 reducer 一起工作。

测试搜索：一个完整的用户场景

搜索会发出两次请求（初始的 React、之后的 JavaScript），所以 mock 要根据 URL 返回不同的数据：

```jsx src/App.test.jsx it('searches for specific stories', async () => { const reactPromise = Promise.resolve({ data: { hits: stories, }, }); const anotherStory = { title: 'JavaScript', url: 'https://en.wikipedia.org/wiki/JavaScript', author: 'Brendan Eich', num_comments: 15, points: 10, objectID: 3, }; const javascriptPromise = Promise.resolve({ data: { hits: [anotherStory], }, }); axios.get.mockImplementation((url) => { if (url.includes('React')) { return reactPromise; } if (url.includes('JavaScript')) { return javascriptPromise; } throw Error(); }); // 初次渲染 render(); // 第一次数据请求 await waitFor(async () => await reactPromise); expect(screen.queryByDisplayValue('React')).toBeInTheDocument(); expect(screen.queryByDisplayValue('JavaScript')).toBeNull(); expect(screen.queryByText('Jordan Walke')).toBeInTheDocument(); expect(screen.queryByText('Dan Abramov, Andrew Clark')).toBeInTheDocument(); expect(screen.queryByText('Brendan Eich')).toBeNull(); // 用户输入 fireEvent.change(screen.queryByDisplayValue('React'), { target: { value: 'JavaScript', }, }); expect(screen.queryByDisplayValue('React')).toBeNull(); expect(screen.queryByDisplayValue('JavaScript')).toBeInTheDocument(); // 用户提交 fireEvent.click(screen.queryByText('Submit')); // 第二次数据请求 await waitFor(async () => await javascriptPromise); expect(screen.queryByText('Jordan Walke')).toBeNull(); expect(screen.queryByText('Dan Abramov, Andrew Clark')).toBeNull(); expect(screen.queryByText('Brendan Eich')).toBeInTheDocument(); }); ```

快照测试

快照测试是一种更轻量的方式：第一次运行时，把组件渲染出的 HTML 结构保存成一个“快照”文件； 之后每次运行都和它对比，结构变了就报告差异。

```jsx src/App.test.jsx describe('SearchForm', () => { ... it('renders snapshot', () => { const { container } = render(); expect(container.firstChild).toMatchSnapshot(); }); }); ```

运行测试后，项目里会多出一个 src/__snapshots__/ 目录。现在去掉 SearchForm 里标签的加粗：

```jsx src/App.jsx Search: ```

测试会失败，并清楚地显示差异：

```console - Expected - 3 + Received + 1 Snapshots 1 failed ```

如果这是意外的改动，就去修代码；如果是有意的改动，在监听模式下按 u 更新快照。 快照文件应该提交到 Git，团队共享。

⚠ 快照测试的局限

快照写起来很快，但它只能说明“和上次不一样了”，不能说明“对不对”。快照太大时，大家往往看都不看就按 u。 适合用在结构稳定、不常改的小组件上，不能代替针对行为的测试。

更现代的做法

mock 请求库 原书写法
```jsx vi.mock('axios'); axios.get.mockImplementationOnce(() => Promise.resolve({ data: { hits: stories } }) ); ```
mock 网络层：MSW 推荐
```jsx import { http, HttpResponse } from 'msw'; import { setupServer } from 'msw/node'; const server = setupServer( http.get('https://hn.algolia.com/api/v1/search', () => HttpResponse.json({ hits: stories }) ) ); // 不管用 fetch 还是 axios，测试都不用改 ```
  • MSW（Mock Service Worker）在网络层拦截请求。好处是测试不依赖你用的是哪个请求库，换掉 axios 测试也不用改。
  • 端到端测试：原书提到 Cypress，现在 Playwright 更为流行，它在真实浏览器里跑完整流程。

小结

  • vi.mock('axios') + mockImplementationOnce / mockImplementation 控制请求返回的数据。
  • await waitFor(…) 或 findBy 等待异步更新；queryBy 用于断言元素不存在。
  • 集成测试从用户视角验证真实结果：数据显示、删除生效、搜索换出新数据。
  • 快照测试能快速发现结构变化，但只适合稳定的小组件。
  • 现代项目常用 MSW mock 网络、用 Playwright 做端到端测试。

动手练习

  2. 为 Item、List、InputWithLabel 各加一个快照测试，看看 __snapshots__ 目录的内容。
  3. 挑战：安装 MSW，把 axios mock 替换为网络层 mock。

面试题

为什么在测试中要 mock 网络请求？

真实请求慢、不稳定、数据不可控，还可能产生副作用。mock 让测试快速、确定、可重复。

waitFor 的作用是什么？

反复执行回调直到其不再抛错或超时，用于等待异步操作导致的状态更新和重新渲染完成。

mockImplementationOnce 和 mockImplementation 的区别？

前者只对下一次调用生效；后者对之后所有调用生效，可以根据参数（如 URL）返回不同结果。

什么是快照测试？适用于什么场景？

保存组件渲染输出并在后续运行时对比差异的测试。适合结构稳定、简单的组件，用来发现意外的结构变化，不能替代行为测试。

MSW 和直接 mock 请求库相比有什么优势？

在网络层拦截请求，与具体请求库解耦；同一套 mock 可用于测试和开发环境。
