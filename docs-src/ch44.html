React 只负责“把组件渲染成界面”，路由、数据请求、状态管理、表单、样式、测试……全都要从生态里挑。 每个方向少则三五个、多则几十个候选库，初学者很容易被淹没。这一部分（第 44–50 章）专门解决这个问题： 先建立一张生态地图和一套选型方法，再逐类比较主流库，最后把它们组合进一个项目。

本章目标

  • 看懂 React 生态的全貌：有哪些类别，每类解决什么问题
  • 掌握一套评估第三方库的清单和工具
  • 知道“什么时候根本不需要引入库”
  • 认出那些已经过时、但在老教程里仍然常见的库

为什么 React 生态这么“乱”

Angular 是“全家桶”：路由、表单、HTTP、测试都是官方提供的，只有一个标准答案。React 是一个库， 官方刻意只做核心，其余交给社区竞争。好处是创新快、可以按需组合；代价就是选择困难，而且“最佳实践”几年就换一轮。

很多库是在 React 或浏览器还缺少某项能力时诞生的。今天，不少需求已经有了内置方案：

★ 每个依赖都有成本

多一个库，就多一份包体积、一份要学的 API、一份需要跟进升级的依赖、一个可能停更的风险。 先用最朴素的方式实现，真正感受到痛点了再引入库 —— 这也是本教程一路手写 reducer、effect 之后才介绍 TanStack Query 的原因： 你知道它解决了什么，才能判断自己需不需要它。

小结

  • React 只做核心，其余由社区竞争：这带来灵活性，也带来选择困难。
  • 引入库之前先问：内置能力能不能解决？自己写几十行行不行？框架是不是自带？
  • 评估库看八个维度：解决问题、维护状态、使用趋势、兼容性、文档与类型、体积、退出成本、团队与许可证。
  • 没有特殊需求时用“默认选择”，风险最小；并学会识别过时的库。

动手练习

  1. 在 npmtrends.com 上对比 zustand、@reduxjs/toolkit、jotai 的下载趋势。
  2. 在 bundlephobia.com 上对比 moment、dayjs、date-fns 的体积。
  3. 挑一个你正在用（或打算用）的库，按本章八个维度写一份简短的评估。
  4. 检查 Hacker Stories 的 package.json：哪些依赖其实可以用内置能力替代？（提示：lodash 的 sortBy。）

面试题

你在项目中如何选择第三方库？

先确认是否真的需要（内置能力、自行实现、框架自带），再从解决问题的契合度、维护活跃度、使用趋势、React 版本与 SSR 兼容性、文档与 TS 支持、包体积、替换成本和许可证等方面比较 2–3 个候选。

为什么不能只看 GitHub 星标？

星标是累计值，不能反映当前的活跃度和使用趋势；应结合下载量趋势、近期发版和社区满意度调查判断。

引入过多第三方库有什么问题？

增加包体积和加载时间、学习和维护成本、升级兼容风险、供应链安全风险，以及库停更后的迁移成本。
