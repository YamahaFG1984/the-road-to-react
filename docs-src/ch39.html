第 21 章留下了一个问题：服务端搜索每敲一个键就发一次请求。第 22 章用“点按钮才搜索”绕开了它， 但很多应用希望边打字边出结果。这一章用防抖正面解决请求过多的问题， 再介绍 React 18/19 的并发渲染工具 useDeferredValue 和 useTransition —— 它们解决的是另一个问题：渲染太慢导致输入卡顿。

本章目标

  • 分清防抖（debounce）和节流（throttle）
  • 写一个 useDebounce 自定义 Hook，实现“停止输入 500ms 后再搜索”
  • 理解“紧急更新”和“非紧急更新”，用 useDeferredValue 让输入保持流畅
  • 用 useTransition 标记非紧急更新并显示 pending 状态
  • 知道这些工具各自适合什么问题

防抖与节流

用户输入 “react” 共 5 次按键。三种处理方式发出的请求数完全不同：

写一个 useDebounce Hook

思路：返回一个“延迟跟随”的值。每次输入变化，就设一个定时器；如果在定时器触发前输入又变了， effect 的清理函数（第 14 章）会取消上一个定时器 —— 这正好就是防抖的“重新计时”：

```jsx src/use-debounce.js import { useEffect, useState } from 'react'; const useDebounce = (value, delay = 500) => { const [debouncedValue, setDebouncedValue] = useState(value); useEffect(() => { const timerId = setTimeout(() => { setDebouncedValue(value); }, delay); // value 在 delay 之内再次变化 → 取消上一个定时器，重新计时 return () => clearTimeout(timerId); }, [value, delay]); return debouncedValue; }; export { useDebounce }; ```

用在服务端搜索上：输入框照常实时更新，请求只跟随防抖后的值：

```jsx src/App.jsx const App = () => { const [searchTerm, setSearchTerm] = useStorageState('search', 'React'); const debouncedSearchTerm = useDebounce(searchTerm, 500); useEffect(() => { if (!debouncedSearchTerm) return; const controller = new AbortController(); dispatchStories({ type: 'STORIES_FETCH_INIT' }); axios .get(`${API_ENDPOINT}${debouncedSearchTerm}`, { signal: controller.signal, }) .then((result) => dispatchStories({ type: 'STORIES_FETCH_SUCCESS', payload: result.data.hits, }) ) .catch((error) => { if (axios.isCancel(error)) return; dispatchStories({ type: 'STORIES_FETCH_FAILURE' }); }); return () => controller.abort(); }, [debouncedSearchTerm]); ... }; ```
💡 防抖 + 取消请求，两者互补

防抖减少了请求次数，但用户停顿后又继续输入时，前一个请求可能还在路上。 第 21 章的 AbortController 负责取消那个已经过时的请求，避免竞态。axios 同样支持 signal 参数。

⚠ 直接用 lodash.debounce 的陷阱

const debouncedFetch = debounce(fetchStories, 500) 写在组件里，每次渲染都会创建一个新的防抖函数， 各自计时，完全起不到防抖作用。要么用 useMemo / useRef 保证它只创建一次，要么用本章“防抖一个值”的思路 —— 后者在 React 里更自然。

另一个问题：渲染太慢

防抖解决的是网络问题。还有一类问题出在渲染上：假设我们在客户端过滤一个很大的列表（比如缓存了 5000 条文章）， 每次按键都要重新过滤并渲染几千个 Item。渲染需要 200ms，这 200ms 里浏览器被占用，输入框就“卡住”了，打字一顿一顿的。

React 18 引入的并发渲染（concurrent rendering）让 React 可以区分更新的轻重缓急：

useDeferredValue：让一个值“慢半拍”

```jsx import { memo, useDeferredValue, useState } from 'react'; const SearchableList = ({ stories }) => { const [query, setQuery] = useState(''); // 输入框用 query（紧急），列表用 deferredQuery（非紧急） const deferredQuery = useDeferredValue(query); const isStale = query !== deferredQuery; return ( <> setQuery(e.target.value)} />
); }; // 配合 memo：deferredQuery 没变时跳过这个昂贵组件 const SlowList = memo(({ stories, query }) => { const filtered = stories.filter((story) => story.title.toLowerCase().includes(query.toLowerCase()) ); return ; }); ```
  • 用户打字时，React 先用新的 query 和旧的 deferredQuery 渲染一次 —— 输入框立刻更新，列表暂时不变。
  • 然后在后台用新的 deferredQuery 渲染列表；如果期间用户又输入了，这次后台渲染会被丢弃，重新开始。
  • query !== deferredQuery 表示列表是“过时”的，可以用半透明提示用户。
  • React 19 起可以传初始值：useDeferredValue(query, '')，首次渲染先用初始值，再在后台渲染真实值。

useTransition：把一次更新标记为非紧急

useDeferredValue 作用于“一个值”；useTransition 作用于“一次状态更新”。 比如切换一个会渲染大量内容的标签页：

```jsx import { useState, useTransition } from 'react'; const Tabs = () => { const [tab, setTab] = useState('stories'); const [isPending, startTransition] = useTransition(); const selectTab = (nextTab) => { startTransition(() => { setTab(nextTab); // 非紧急：可以被打断，旧界面先保持 }); }; return ( <> {isPending && Loading…} {tab === 'stories' ? : } ); }; ```

React 19 更进一步：startTransition 可以接收 async 函数。整个异步过程中 isPending 都为 true， 这就是第 24 章 form Actions 的底层机制 —— <form action> 本质上就是自动包在 transition 里的 async 函数。

```jsx const [isPending, startTransition] = useTransition(); const handleSave = () => { startTransition(async () => { await saveStory(story); // 异步期间 isPending === true startTransition(() => { // await 之后的状态更新再包一层（React 19 的已知限制） setSaved(true); }); }); }; ```
ⓘ transition 与 Suspense 配合

当一次更新会让已显示的内容重新“暂停”（比如路由切换到一个需要加载数据的页面），如果这次更新在 transition 中， React 会保持旧界面而不是立刻换成 Suspense 的 fallback。React Router 的导航默认就是这样做的。

怎么选

工具解决什么原理会减少网络请求吗
显式提交（第 22 章）请求过多用户点了才请求会
防抖 useDebounce请求过多固定延迟，停下来才执行会
节流持续事件太频繁固定频率执行会
useDeferredValue渲染太慢导致输入卡顿值的渲染降为低优先级，可打断不会（常和防抖一起用）
useTransition某次更新渲染太慢；异步操作的 pending更新降为低优先级，提供 isPending不会
过去 React 17 及以前
```jsx // 只能用防抖“掩盖”慢渲染： // 故意延迟更新，希望用户停下来时再卡 const debouncedFilter = useMemo( () => debounce(setFilter, 300), [] ); ```
现在 React 18+ / 19
```jsx // 渲染层面的调度：不用固定延迟， // 设备快就马上更新，设备慢就自动让路 const deferredFilter = useDeferredValue(filter); // 异步操作的 pending 由 React 追踪 startTransition(async () => { … }); ```

小结

  • 防抖：等停止触发一段时间后执行一次，适合搜索框；节流：固定频率执行，适合滚动等持续事件。
  • useDebounce 利用 effect 清理函数取消上一个定时器，几行代码就能实现；配合 AbortController 处理竞态。
  • 并发渲染把更新分为紧急和非紧急：useDeferredValue 延后一个值的渲染，useTransition 把一次更新标记为非紧急并提供 isPending。
  • 防抖减少请求次数；并发特性解决渲染卡顿。两者可以同时使用。

面试题

防抖和节流有什么区别？

防抖在触发停止一段时间后才执行一次（每次触发都重新计时）；节流保证在固定时间间隔内最多执行一次。搜索输入常用防抖，滚动、缩放常用节流。

如何在 React 中实现防抖？

常见方式是自定义 Hook：在 effect 中 setTimeout 更新防抖值，并在清理函数中 clearTimeout。直接使用工具库的 debounce 时需用 useMemo/useRef 保持同一个函数实例。

useDeferredValue 和防抖有什么区别？

防抖使用固定延迟并减少执行次数；useDeferredValue 没有固定延迟，而是让基于该值的渲染以低优先级进行、可被打断，不会减少网络请求。

useTransition 有什么用？

把状态更新标记为非紧急，使其渲染可被更紧急的更新（如输入）打断，并提供 isPending 显示过渡状态；React 19 中还支持 async 函数，用于追踪异步操作。

并发特性需要什么前提？

使用 React 18+ 的 createRoot（旧的 ReactDOM.render 以同步模式运行，不支持并发特性）。
