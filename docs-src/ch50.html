测试：统一的 Provider 与 MSW

MSW 在网络层拦截请求（第 31 章），所以无论请求是从 loader 还是 useQuery 发出，测试都不需要关心。

⚠ 模板不是必选清单

上面的每一项都应该是“遇到了对应的问题才加进来”。一个只有三个页面的小应用配齐八个库，维护成本会远超它带来的收益。 回到第 44 章的决策流程：先问需不需要，再问选哪个。

小结

  • 组合的核心原则：URL、服务端、全局客户端、表单、局部 UI 五类状态，每类只归一个库管，同一份数据不存两处。
  • 按功能组织目录，用自己的模块（api.ts、store、lib/）包装第三方库，方便替换。
  • Provider 按依赖关系嵌套：被依赖的在外层；Zustand 不需要 Provider。
  • queryOptions 让路由 loader 和组件共享同一份查询定义。
  • 测试时用带 Provider 的 render 工具 + MSW。
  • 根据项目类型选择模板，但每一项都要有引入的理由。

面试题

一个 React 项目里多个状态库如何分工？

按状态类别分工：服务端数据交给 TanStack Query 等缓存库，可分享状态放 URL（路由），全局客户端状态用 Context 或 Zustand/Redux，表单状态用表单库，局部 UI 状态用 useState；避免同一份数据存在多处。

为什么要用自己的模块包装第三方库？

集中配置和约定（如 queryKey、请求地址），减少组件对具体库的依赖，将来替换或升级时只需修改一处。

Provider 的嵌套顺序有什么讲究？

被依赖的 Provider 放在外层。例如路由 loader 需要访问 queryClient，QueryClientProvider 应包在 RouterProvider 外面。

测试使用 TanStack Query 的组件需要注意什么？

为每个测试创建新的 QueryClient（避免缓存共享），关闭重试以便快速失败，并用 MSW 等方式模拟网络请求。
