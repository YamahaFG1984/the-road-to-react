乐观更新

给每篇文章加一个 ▲ Upvote 按钮。点击后要请求服务器，假设需要 1 秒。如果老老实实等服务器返回再更新数字， 用户会觉得“点了没反应”。乐观更新的做法是：先假设会成功，立刻把数字加 1； 服务器返回成功就保持，失败就退回去。社交网站的点赞几乎都是这么做的。

useOptimistic

```jsx src/Upvote.jsx import { useOptimistic, useState, startTransition } from 'react'; // 模拟一个会随机失败的 API const upvoteStory = (id) => new Promise((resolve, reject) => setTimeout(() => (Math.random() > 0.2 ? resolve() : reject()), 1000) ); const Upvote = ({ story }) => { const [points, setPoints] = useState(story.points); // 乐观值：平时等于 points；action 进行中可以临时“超前” const [optimisticPoints, addOptimisticPoint] = useOptimistic( points, (currentPoints, increment) => currentPoints + increment ); const handleUpvote = () => { startTransition(async () => { addOptimisticPoint(1); // ① 立即显示 +1 try { await upvoteStory(story.objectID); // ② 请求服务器 startTransition(() => setPoints((p) => p + 1)); // ③ 成功：写入真实状态 } catch { alert('Upvote failed'); // ④ 失败：什么都不用做，transition 结束后乐观值自动回到 points } }); }; return ( ); }; ```
ⓘ 注意事项
  • addOptimistic 必须在 action 或 startTransition 内调用；在 <form action> 的函数里调用时已经自动满足。
  • “成功后写入真实状态”那一步不能省：否则 transition 结束后界面也会回到旧值。
  • 使用 TanStack Query（第 40 章）时，可以用 useMutation 的 onMutate 修改缓存、onError 回滚，思路相同。

怎么选

场景推荐
一两个字段、提交时校验即可（搜索、登录、留言）HTML 原生校验 + form action / useActionState
使用 Next.js 服务端函数，校验本来就在服务器做useActionState + Zod（前后端共用 schema）
字段多、需要实时校验、动态字段、多步骤表单React Hook Form + Zod
偏好类型推导更强的新方案TanStack Form（第 48 章）

小结

  • 乐观更新：先按成功显示，失败回滚。useOptimistic 的乐观值只在 action 期间生效，回滚是自动的。
  • 校验分三层：HTML 原生（零成本）、客户端 schema（体验）、服务端（安全，必须有）。
  • Zod 用 schema 描述数据规则，可推导 TS 类型，可前后端共用。
  • 简单表单用 useActionState + Zod；复杂表单用 React Hook Form + Zod。

面试题

什么是乐观更新？有什么风险？

在服务器确认之前先更新界面，假设操作会成功，失败时回滚。风险是失败时界面会“跳回去”，因此适用于成功率高、可逆的操作，并需要给出失败提示。

useOptimistic 是如何实现回滚的？

乐观值只在 action / transition 进行期间覆盖真实状态；transition 结束后显示回到真实状态。成功时需要更新真实状态，失败时不改即自动回滚。

为什么有了前端校验还需要后端校验？

前端校验可以被绕过（修改脚本或直接调用接口），只能提升体验；后端校验才能保证数据安全和正确。

React Hook Form 为什么性能好？

默认使用非受控输入，通过 ref 读取值，输入时不会触发整个表单组件重新渲染；只在需要时（如错误变化）更新。
