App 里现在有三个彼此相关的状态：stories、isLoading、isError。 它们各自独立更新，稍不留神就会组合出“既在加载、又出错了”这种不可能的状态。 这一章引入 useReducer，把相关的状态和它们的变化规则收拢到一个地方。

本章目标

  • 理解 reducer：(state, action) => newState
  • 用 useReducer 和 dispatch 管理列表状态
  • 识别“不可能状态”，并用一个 reducer 管理一组相关状态来避免它
  • 知道什么时候用 useState，什么时候用 useReducer

什么是 reducer

reducer 是一个纯函数：给它当前状态和一个描述“发生了什么”的动作（action），它返回新的状态。 动作通常是一个带 type 的对象，需要额外数据时再带一个 payload：

先写一个只处理一种动作的 reducer，放在组件外面：

```jsx src/App.jsx const storiesReducer = (state, action) => { if (action.type === 'SET_STORIES') { return action.payload; } else { throw new Error(); } }; ```

遇到没处理的动作类型就抛出错误 —— 提醒自己“这里漏写了”。

useReducer

在 App 里用 useReducer 替换 useState。它接收 reducer 和初始状态，返回 [当前状态, dispatch 函数]：

```jsx src/App.jsx import { useState, useEffect, useRef, useReducer } from 'react'; const App = () => { ... const [stories, dispatchStories] = useReducer(storiesReducer, []); ... }; ```

以前用 setStories(新值) 直接设置状态；现在用 dispatchStories(动作) 派发一个动作， 由 reducer 决定新状态是什么：

```jsx src/App.jsx const App = () => { ... useEffect(() => { setIsLoading(true); getAsyncStories() .then((result) => { dispatchStories({ type: 'SET_STORIES', payload: result.data.stories, }); setIsLoading(false); }) .catch(() => setIsError(true)); }, []); const handleRemoveStory = (item) => { const newStories = stories.filter( (story) => item.objectID !== story.objectID ); dispatchStories({ type: 'SET_STORIES', payload: newStories, }); }; ... }; ```

只有一种动作的 reducer 没什么意义。删除逻辑也可以挪进 reducer：组件只说“删掉这一篇”（做什么）， reducer 负责“怎么删”（怎么做）—— 又是一次从命令式到声明式的转变：

```jsx src/App.jsx const handleRemoveStory = (item) => { dispatchStories({ type: 'REMOVE_STORY', payload: item, }); }; ``` ```jsx src/App.jsx const storiesReducer = (state, action) => { switch (action.type) { case 'SET_STORIES': return action.payload; case 'REMOVE_STORY': return state.filter( (story) => action.payload.objectID !== story.objectID ); default: throw new Error(); } }; ```

动作多了以后 if / else 会很乱，switch 是社区里写 reducer 的惯用方式。

不可能状态

用多个 useState 并没有错，但当你看到好几个 setter 连着调用时要警惕。做个实验，让假 API 失败：

```jsx src/App.jsx const getAsyncStories = () => new Promise((resolve, reject) => setTimeout(reject, 2000)); ```

两秒后页面上同时显示 “Something went wrong ...” 和 “Loading ...”：catch 里设置了 isError， 却忘了把 isLoading 设回 false。“正在加载”和“加载失败”本不该同时成立，这就是不可能状态。 这类 bug 很难发现，因为每个状态单独看都没错。

把相关状态合并进一个 reducer

把这三个状态：

```jsx src/App.jsx const [stories, dispatchStories] = useReducer(storiesReducer, []); const [isLoading, setIsLoading] = useState(false); const [isError, setIsError] = useState(false); ```

合并成一个 reducer 管理的对象：

```jsx src/App.jsx const [stories, dispatchStories] = useReducer(storiesReducer, { data: [], isLoading: false, isError: false, }); ```

数据获取过程中的每一步都改为派发动作：

```jsx src/App.jsx useEffect(() => { dispatchStories({ type: 'STORIES_FETCH_INIT' }); getAsyncStories() .then((result) => { dispatchStories({ type: 'STORIES_FETCH_SUCCESS', payload: result.data.stories, }); }) .catch(() => dispatchStories({ type: 'STORIES_FETCH_FAILURE' }) ); }, []); ```

reducer 要处理新的动作，并且状态从数组变成了对象：

```jsx src/App.jsx const storiesReducer = (state, action) => { switch (action.type) { case 'STORIES_FETCH_INIT': return { ...state, isLoading: true, isError: false, }; case 'STORIES_FETCH_SUCCESS': return { ...state, isLoading: false, isError: false, data: action.payload, }; case 'STORIES_FETCH_FAILURE': return { ...state, isLoading: false, isError: true, }; case 'REMOVE_STORY': return { ...state, data: state.data.filter( (story) => action.payload.objectID !== story.objectID ), }; default: throw new Error(); } }; ```

每个分支都用展开运算符复制当前状态，再覆盖需要改的字段。STORIES_FETCH_FAILURE 同时把 isLoading 设为 false、isError 设为 true —— 上面的 bug 就这样消失了。

🔎 深入一点：更彻底的做法

用一个 status 字段代替多个布尔值：'idle' | 'loading' | 'success' | 'error'。 一个字段同一时刻只能有一个值，“既加载又出错”在结构上就不可能出现。这是“状态机”思想的最简形式， 配合 TypeScript（第 29 章）效果更好。

ⓘ 和 Redux 的关系

如果你听说过 Redux：它的核心就是 reducer + action + dispatch，只不过管理的是整个应用的全局状态。 useReducer 把同样的模式带进了单个组件。早年“用 React 就要配 Redux”的观念已经过时， 今天大多数应用用组件状态 + Context 就够了，需要时再考虑 Redux Toolkit、Zustand 等库。

小结

  • reducer 是纯函数 (state, action) => newState；useReducer(reducer, initialState) 返回 [state, dispatch]。
  • 组件派发“发生了什么”，reducer 决定“状态怎么变”；用 switch 组织多个动作。
  • 多个相关的 useState 分别更新容易产生不可能状态；合并到一个 reducer 里，每次转换都完整描述结果。
  • 简单独立的值用 useState，相互关联或逻辑复杂的状态用 useReducer。

动手练习

  1. 把动作类型 'STORIES_FETCH_INIT' 等提取成常量，在 reducer 和 dispatch 处复用，避免拼写错误。
  2. 用会失败的假 API 验证错误处理，然后改回成功的版本。
  3. 挑战：用一个 status 字段代替 isLoading 和 isError，并相应修改 JSX。
  4. （选读）了解“什么时候用 useState、什么时候用 useReducer”，以及“从 props 派生 state”的常见误区。

面试题

什么是 useReducer？和 useState 有什么区别？

通过派发动作、由 reducer 函数计算新状态来管理状态的 Hook。useState 适合简单独立的值；useReducer 适合多个相互依赖的值或复杂的更新逻辑。

reducer 函数的基本结构是什么？

接收当前 state 和 action，根据 action.type 返回新的 state，不修改原 state、没有副作用。

什么是“不可能状态”？

在业务上不应同时成立的状态组合（如同时 loading 与 error）。多个独立状态分别更新时容易出现。

reducer 如何帮助避免不可能状态？

把相关状态放在一个对象里，由集中定义的转换一次性设置所有字段，减少遗漏；进一步可用单一 status 字段在结构上杜绝。

useReducer 能完全替代 useState 吗？

技术上可以（useState 内部就是基于 reducer 的），但对简单状态来说 useState 更直观，没必要替代。
