Context：跨层级传递数据

第 18 章里 onRemoveItem 从 App 经过 List 才到达 Item —— List 自己根本不用它，只是个“二传手”。 层级一深，这种 prop drilling（属性钻透）会很烦人。Context 让祖先组件把数据“广播”给整个子树， 任何后代都可以直接读取：

JSX
import { createContext, use } from 'react';

// 1. 创建 Context（可给默认值）
const ThemeContext = createContext('light');

// 2. 在上层提供值
const App = () => (
  <ThemeContext value="dark">
    <Layout />
  </ThemeContext>
);

// 3. 在任意后代里读取
const Item = () => {
  const theme = use(ThemeContext);
  return <li className={theme}>…</li>;
};
React 18 及以前 旧写法
JSX
import { useContext } from 'react';

<ThemeContext.Provider value="dark">
  <Layout />
</ThemeContext.Provider>

const theme = useContext(ThemeContext);
React 19 新写法
JSX
import { use } from 'react';

<ThemeContext value="dark">
  <Layout />
</ThemeContext>

const theme = use(ThemeContext);
  • React 19 可以直接把 Context 当作 Provider 使用，<Context.Provider> 仍然可用，但将来会被废弃。
  • useContext 依然有效；新的 use 也能读取 Context，而且（和其他 Hook 不同）可以在 if 里调用。
  • Context 的值变化时，所有读取它的组件都会重新渲染。它适合“低频变化、很多地方要用”的数据：主题、当前用户、语言。
ⓘ 为什么本书没把 Context 用在 Hacker Stories 里

我们的应用只有三四层组件，prop drilling 还不构成问题。强行引入 Context 只会让代码更复杂，却看不出它解决了什么。 对初学者来说它像一道坎，对中级开发者来说又像过早优化。遇到“同一个值要穿过很多层”的时候，再用它不迟。 另外别忘了第 16 章的组件组合，它常常是比 Context 更简单的解法。

use() 与 Suspense：另一种读取异步数据的方式

use 不仅能读 Context，还能读 Promise。组件“读取”一个还没兑现的 Promise 时会暂停（suspend）， React 转而显示最近的 <Suspense> 边界提供的 fallback；Promise 兑现后再回来继续渲染：

JSX
import { use, Suspense } from 'react';

const StoryList = ({ storiesPromise }) => {
  const stories = use(storiesPromise); // 没好就“挂起”
  return <List list={stories} />;
};

const App = ({ storiesPromise }) => (
  <Suspense fallback={<p>Loading ...</p>}>
    <StoryList storiesPromise={storiesPromise} />
  </Suspense>
);
⚠ 不要在组件里直接创建 Promise 再 use 它

const stories = use(fetch(url)) 这样写，每次渲染都会创建一个新 Promise，组件会不停地挂起、重新请求。 传给 use 的 Promise 必须是稳定的（在组件外创建、被缓存、或由服务端组件传下来）。 这就是为什么这种写法通常和框架或数据请求库一起用。

服务端组件与服务端函数

React 19 正式稳定了两项“全栈”特性：

🖥️

服务端组件（Server Components）

只在服务器（或构建时）运行的组件。可以直接 await 数据库查询，代码不会发送到浏览器，包体积更小。

📤

服务端函数（Server Functions）

标记了 'use server' 的函数，可以在客户端作为 form action 调用，实际在服务器上执行 —— 不必手写 API。

JSX
// 服务端组件：直接在组件里 await 数据（运行在服务器上）
const StoriesPage = async () => {
  const stories = await db.stories.findMany();
  return <List list={stories} />;
};

// 服务端函数：在表单里当作 action 使用
async function createStory(formData) {
  'use server';
  await db.stories.create({ title: formData.get('title') });
}

它们需要打包器和服务器的深度配合，所以只能在支持它们的框架里使用（最成熟的是 Next.js）。 纯 Vite 客户端项目（本教程）用不上它们，但理解第 1 章“服务器渲染 vs 客户端渲染”的历史后，你会发现它们正是钟摆摆回服务器的结果。

组件模式

你已经学过组件组合（第 16 章）和可复用组件。社区里还有两种经典模式：render props 和高阶组件（HOC）。 自从有了自定义 Hook（第 15 章），它们用得少了很多，但在大型老项目和一些库里依然会遇到，建议有空时了解一下。

面试题

什么是 Context？什么时候使用？

一种让祖先组件向任意深度的后代组件提供数据、而无需逐层传 props 的机制。适合主题、当前用户、语言等全局且变化不频繁的数据。

React 19 中 Context 的写法有什么变化？

可以直接用 <MyContext value={…}> 作为 Provider；可以用新的 use(MyContext) 读取，且 use 可以在条件语句中调用。

use() 和其他 Hook 有什么不同？

它可以读取 Context 或 Promise，并且可以在条件和循环中调用；读取未完成的 Promise 时会触发 Suspense。

什么是服务端组件？

只在服务器端（或构建时）渲染的组件，可以直接访问服务端资源，其代码不会打包到客户端，需要框架支持。
