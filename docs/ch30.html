测试入门：Vitest

测试是专业开发者的必修课：它让你在代码上线之前就确认它按预期工作，也让你以后敢放心地重构。 这一章搭建 Vitest + React Testing Library 测试环境，先测试一个普通函数（reducer）， 再测试单个组件。下一章再做完整的集成测试。

本章目标

  • 理解测试金字塔：单元测试、集成测试、端到端测试
  • 用 Vitest 写测试套件、测试用例和断言
  • 为 reducer 编写单元测试，分清 toBe 和 toStrictEqual
  • 用 React Testing Library 渲染组件、查找元素、模拟用户操作

测试金字塔

工具选择上，我们用社区最流行的组合：Vitest 是测试框架（运行测试、组织用例、断言、mock）， React Testing Library（RTL）负责渲染组件、查找元素、触发事件。

安装 Vitest

命令行
npm install vitest --save-dev

在 package.json 里加一个 test 脚本：

package.json
{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "test": "vitest",
    "lint": "eslint .",
    "preview": "vite preview"
  }
}

在 src/App.jsx 旁边新建 src/App.test.jsx。Vitest 会自动找到所有 .test.jsx（以及 .spec.jsx 等）文件。

测试套件、测试用例与断言

src/App.test.jsx
import { describe, it, expect } from 'vitest';

describe('something truthy and falsy', () => {
  it('true to be true', () => {
    expect(true).toBe(true);
  });

  it('false to be false', () => {
    expect(false).toBe(false);
  });
});

运行 npm run test：

控制台输出

💡 开两个终端

npm run test 默认是监听模式：你改代码或测试，它自动重跑（按 h 看快捷键，a 全部重跑，f 只跑失败的）。 建议一个终端开着 npm run dev，另一个开着 npm run test。

单元测试：函数

要测试 App.jsx 里的东西，先用具名导出把它们导出来：

src/App.jsx
...

export default App;

export { storiesReducer, SearchForm, InputWithLabel, List, Item };
src/App.test.jsx
import { describe, it, expect } from 'vitest';

import App, {
  storiesReducer,
  Item,
  List,
  SearchForm,
  InputWithLabel,
} from './App';

const storyOne = {
  title: 'React',
  url: 'https://react.dev/',
  author: 'Jordan Walke',
  num_comments: 3,
  points: 4,
  objectID: 0,
};

const storyTwo = {
  title: 'Redux',
  url: 'https://redux.js.org/',
  author: 'Dan Abramov, Andrew Clark',
  num_comments: 2,
  points: 5,
  objectID: 1,
};

const stories = [storyOne, storyTwo];

reducer 是最适合单元测试的对象：纯函数，给定输入，检查输出。所有 reducer 测试都是同一个模式 ——给定状态和动作，期望得到某个新状态：

src/App.test.jsx
describe('storiesReducer', () => {
  it('removes a story from all stories', () => {
    const action = { type: 'REMOVE_STORY', payload: storyOne };
    const state = { data: stories, isLoading: false, isError: false };

    const newState = storiesReducer(state, action);

    const expectedState = {
      data: [storyTwo],
      isLoading: false,
      isError: false,
    };

    expect(newState).toStrictEqual(expectedState);
  });
});

如果写成 toBe，测试会失败：reducer 返回的是一个新对象（这正是不可变更新该有的样子）， 它和 expectedState 内容相同但不是同一个对象。toEqual 也比较内容，但会忽略 undefined 属性等差异， toStrictEqual 更严格。

为组件测试做准备

测试不会打开真正的浏览器，但组件渲染出的 HTML 总得有个地方放。jsdom 用 JavaScript 模拟了一个浏览器 DOM 环境。 再装上 React Testing Library：

命令行
npm install jsdom --save-dev
npm install @testing-library/react @testing-library/jest-dom --save-dev
vite.config.js
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  test: {
    environment: 'jsdom',
    setupFiles: './tests/setup.js',
  },
});
tests/setup.js
import { afterEach } from 'vitest';
import { cleanup } from '@testing-library/react';
import '@testing-library/jest-dom/vitest';

// 每个测试结束后卸载渲染的组件，避免互相影响
afterEach(() => {
  cleanup();
});

@testing-library/jest-dom/vitest 给 expect 增加了一批 DOM 专用断言，比如 toBeInTheDocument()、toHaveAttribute()。 （原书用的是 expect.extend(matchers) 的手动写法，效果相同。）

单元测试：组件

从 Item 开始：给它 props（输入），检查渲染出的 HTML（输出）。第一步永远是先看看渲染出了什么：

src/App.test.jsx
import { describe, it, expect, vi } from 'vitest';
import { render, screen, fireEvent } from '@testing-library/react';

...

describe('Item', () => {
  it('renders all properties', () => {
    render(<Item item={storyOne} />);

    screen.debug();
  });
});
控制台输出
<body>
  <div>

      <span>

      </span>
      <span>Jordan Walke</span>

养成习惯：每渲染一个新组件，先 screen.debug() 看一眼，再决定查找什么、断言什么。

src/App.test.jsx
describe('Item', () => {
  it('renders all properties', () => {
    render(<Item item={storyOne} />);

    expect(screen.getByText('Jordan Walke')).toBeInTheDocument();
    expect(screen.getByText('React')).toHaveAttribute(
      'href',
      'https://react.dev/'
    );
  });

  it('renders a clickable dismiss button', () => {
    render(<Item item={storyOne} />);

    expect(screen.getByRole('button')).toBeInTheDocument();
  });
});

查找元素的方式

RTL 的核心理念是：像用户一样使用组件。用户看不到组件树和类名，只看到文字、按钮、输入框。 所以查找方法也是按“用户能感知到的东西”来的，推荐的优先级如下：

查询按什么找例子
getByRole 首选可访问性角色 + 名字getByRole('button', { name: 'Dismiss' })
getByLabelText表单控件的 labelgetByLabelText(/Search/)
getByPlaceholderTextplaceholdergetByPlaceholderText('Search…')
getByText可见文字getByText('Jordan Walke')
getByDisplayValue输入框当前的值getByDisplayValue('React')
getByTestIddata-testid 属性最后的手段

每种查询都有几个变体：getBy（找一个，找不到就报错）、getAllBy（找多个）、 queryBy（找不到返回 null，用于断言“不存在”）、findBy（异步等待出现）。 写 getByRole('') 这种不存在的角色时，RTL 会贴心地列出页面上所有可用的角色。

测试回调：mock 函数

点击 Dismiss 应该调用 onRemoveItem。我们不关心它具体做什么，只关心它被调用了。 用 vi.fn() 创建一个 mock 函数，它会记录自己被调用的次数和参数：

src/App.test.jsx
it('clicking the dismiss button calls the callback handler', () => {
  const handleRemoveItem = vi.fn();

  render(<Item item={storyOne} onRemoveItem={handleRemoveItem} />);

  fireEvent.click(screen.getByRole('button'));

  expect(handleRemoveItem).toHaveBeenCalledTimes(1);
  expect(handleRemoveItem).toHaveBeenCalledWith(storyOne);
});

注意这里并没有测试“文章真的从列表里消失了” —— 删除逻辑在 App 里，Item 只负责通知。 单元测试只关心这一块积木本身是否正常；把积木拼在一起的测试留给下一章。

测试 SearchForm

src/App.test.jsx
describe('SearchForm', () => {
  const searchFormProps = {
    searchTerm: 'React',
    onSearchInput: vi.fn(),
    searchAction: vi.fn(),
  };

  it('renders the input field with its value', () => {
    render(<SearchForm {...searchFormProps} />);

    expect(screen.getByDisplayValue('React')).toBeInTheDocument();
  });

  it('renders the correct label', () => {
    render(<SearchForm {...searchFormProps} />);

    expect(screen.getByLabelText(/Search/)).toBeInTheDocument();
  });

  it('calls onSearchInput on input field change', () => {
    render(<SearchForm {...searchFormProps} />);

    fireEvent.change(screen.getByDisplayValue('React'), {
      target: { value: 'Redux' },
    });

    expect(searchFormProps.onSearchInput).toHaveBeenCalledTimes(1);
  });

  it('calls searchAction on button submit click', () => {
    render(<SearchForm {...searchFormProps} />);

    fireEvent.click(screen.getByRole('button'));

    expect(searchFormProps.searchAction).toHaveBeenCalledTimes(1);
  });
});

/Search/ 是正则表达式，匹配“包含 Search”的文字 —— 用字符串就得写全 'Search:'。 另外注意，虽然 SearchForm 内部还渲染了 InputWithLabel，RTL 渲染的是完整的 HTML， 测试并不关心组件是怎么拆分的 —— 用户也不关心。

新旧对照

fireEvent 原书写法
JSX
import { fireEvent } from '@testing-library/react';

fireEvent.change(input, { target: { value: 'Redux' } });
fireEvent.click(button);
user-event 官方更推荐
JSX
import userEvent from '@testing-library/user-event';

const user = userEvent.setup();
await user.clear(input);
await user.type(input, 'Redux'); // 逐个字符，像真人打字
await user.click(button);        // 包含 hover、focus 等完整过程
过去现在
Create React App 自带 JestVite 项目多用 Vitest（与 Jest API 几乎一致，配置复用 Vite）
Enzyme：测试组件内部 state、实例方法Enzyme 已停止维护，没有支持 React 18+ 的官方适配器；改用 RTL，测试用户看得到的行为
react-test-rendererReact 19 中已废弃，官方建议迁移到 RTL

小结

  • 测试金字塔：大量单元测试、适量集成测试、少量端到端测试。
  • Vitest：describe 组织套件，it 写用例，expect(…).toXxx() 断言；对象用 toStrictEqual。
  • reducer 测试模式：给定 state 和 action，断言新 state。
  • RTL：render 渲染、screen.debug 查看、getByRole 等按用户视角查找、fireEvent / user-event 触发交互、vi.fn() 验证回调。

面试题

单元测试、集成测试、端到端测试有什么区别？

单元测试验证单个函数或组件；集成测试验证多个单元协同工作；端到端测试在真实浏览器中模拟完整的用户流程。越往上越接近真实、越慢越贵。

toBe 和 toStrictEqual 的区别？

toBe 用 Object.is 比较（对象比较引用）；toStrictEqual 递归比较内容与结构，适合对象和数组。

React Testing Library 的核心理念是什么？

测试用户看到和使用的行为，而不是组件的实现细节；因此按角色、标签、文字等用户可感知的方式查询元素。

getBy、queryBy、findBy 有什么区别？

getBy 找不到时抛错；queryBy 找不到返回 null，适合断言元素不存在；findBy 返回 Promise，等待元素异步出现。

什么是 mock 函数？

用于替代真实函数的测试替身（如 vi.fn()），记录调用次数和参数，便于断言组件是否正确调用了回调。
