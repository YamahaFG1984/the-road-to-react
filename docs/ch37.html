Context 实战

第 25 章只是认识了 Context。这一章在 Hacker Stories 里做两个真实需求：深色 / 浅色主题切换和收藏夹。 两者都是“很多组件都要用、隔了好几层”的数据，正是 Context 的用武之地。同时我们也会讨论 Context 的代价，以及什么时候不该用它。

本章目标

  • 用“Provider 组件 + 自定义 Hook”的模式封装 Context
  • 把 Context 和 useReducer、localStorage 组合起来
  • 理解 Context 值变化时的重新渲染范围，以及拆分 Context 的技巧
  • 判断什么时候该用 Context，什么时候用组合、URL 或专门的库

需求：收藏夹

每条文章旁边放一个 ☆ 按钮，点击后加入收藏；页头显示“已收藏 N 篇”。收藏数据需要被两个相距很远的组件使用：

按第 11 章的规则，状态要提升到它们的共同祖先 App，然后一路用 props 传下去 —— Layout、StoriesPage、List 都得转手。 这就是 prop drilling。而且现在有了路由（第 36 章），列表页由路由渲染，想从 App 传 props 下去更加别扭。

推荐模式：Provider 组件 + 自定义 Hook

不要把 createContext 散落在各处使用。把 Context、状态逻辑和读取方式封装在一个文件里：

src/favorites.jsx
import { createContext, use, useReducer, useEffect } from 'react';

const FavoritesContext = createContext(null);

const favoritesReducer = (state, action) => {
  switch (action.type) {
    case 'TOGGLE_FAVORITE': {
      const story = action.payload;
      const exists = state.some((s) => s.objectID === story.objectID);
      return exists
        ? state.filter((s) => s.objectID !== story.objectID)
        : [...state, story];
    }
    case 'CLEAR_FAVORITES':
      return [];
    default:
      throw new Error();
  }
};

const loadFavorites = () =>
  JSON.parse(localStorage.getItem('favorites') ?? '[]');

// 1. Provider 组件：持有状态，并把它提供给整个子树
const FavoritesProvider = ({ children }) => {
  const [favorites, dispatch] = useReducer(
    favoritesReducer,
    undefined,
    loadFavorites // 惰性初始化：只在首次渲染时读取 localStorage
  );

  useEffect(() => {
    localStorage.setItem('favorites', JSON.stringify(favorites));
  }, [favorites]);

  return (
    <FavoritesContext value={{ favorites, dispatch }}>
      {children}
    </FavoritesContext>
  );
};

// 2. 自定义 Hook：统一的读取入口，并检查是否在 Provider 内使用
const useFavorites = () => {
  const context = use(FavoritesContext);

  if (!context) {
    throw new Error('useFavorites must be used within a FavoritesProvider');
  }

  const { favorites, dispatch } = context;

  return {
    favorites,
    isFavorite: (story) =>
      favorites.some((s) => s.objectID === story.objectID),
    toggleFavorite: (story) =>
      dispatch({ type: 'TOGGLE_FAVORITE', payload: story }),
    clearFavorites: () => dispatch({ type: 'CLEAR_FAVORITES' }),
  };
};

export { FavoritesProvider, useFavorites };

在应用的上层包一次 Provider（放在路由外面，所有页面都能用）：

src/main.jsx
createRoot(document.getElementById('root')).render(
  <StrictMode>
    <FavoritesProvider>
      <RouterProvider router={router} />
    </FavoritesProvider>
  </StrictMode>
);

任何组件都可以直接使用，中间层一行都不用改：

JSX
// 页头
const Header = () => {
  const { favorites } = useFavorites();
  return <span>★ {favorites.length} saved</span>;
};

// 列表项
const Item = ({ item, onRemoveItem }) => {
  const { isFavorite, toggleFavorite } = useFavorites();

  return (
    <li>
      ...
      <button
        type="button"
        aria-pressed={isFavorite(item)}
        onClick={() => toggleFavorite(item)}
      >
        {isFavorite(item) ? '★' : '☆'}
      </button>
    </li>
  );
};
★ 为什么要这样封装
  • 隐藏实现：使用方不关心数据存在 Context 还是别的地方。
  • 尽早报错：忘了包 Provider 时，得到一条清晰的错误，而不是莫名其妙的 undefined。
  • 业务方法集中：toggleFavorite 这样的操作写在一处，而不是每个组件都去 dispatch。

主题切换

主题是 Context 最经典的用例：值很少变化，却几乎每个组件都可能用到。

src/theme.jsx
import { createContext, use, useEffect } from 'react';

const ThemeContext = createContext(null);

const ThemeProvider = ({ children }) => {
  const [theme, setTheme] = useStorageState('theme', 'light'); // 第 15 章的 Hook

  useEffect(() => {
    // 同步到 <html data-theme="dark">，CSS 根据它切换颜色变量
    document.documentElement.dataset.theme = theme;
  }, [theme]);

  const toggleTheme = () =>
    setTheme((current) => (current === 'light' ? 'dark' : 'light'));

  return (
    <ThemeContext value={{ theme, toggleTheme }}>
      {children}
    </ThemeContext>
  );
};

const useTheme = () => {
  const context = use(ThemeContext);
  if (!context) throw new Error('useTheme must be used within a ThemeProvider');
  return context;
};

export { ThemeProvider, useTheme };
src/index.css
:root {
  --bg: #ffffff;
  --fg: #171212;
}

[data-theme='dark'] {
  --bg: #171212;
  --fg: #f5f5f5;
}

body {
  background: var(--bg);
  color: var(--fg);
}

注意这里的分工：React 只负责“当前是哪个主题”这一个状态，颜色的切换交给 CSS 变量完成。 这样主题变化时，大部分组件根本不需要重新渲染 —— 它们的样式由浏览器自动更新。

Context 的代价：重新渲染

Context 的值一变，所有读取这个 Context 的组件都会重新渲染，即使它们只用到了值的一小部分。 而且注意上面 Provider 里的 value={{ favorites, dispatch }}：每次 Provider 渲染都会创建一个新对象， 消费者会认为值变了。

几个常用的优化手段：

  • 按关注点拆分：主题、收藏、用户各一个 Context，互不影响。
  • 稳定 value：用 useMemo 包住 value 对象（启用 React Compiler 时会自动处理）。
  • 拆分“读”和“写”：dispatch 永远不变，可以放进单独的 Context。只负责触发操作的组件（比如一个“清空收藏”按钮）读取 dispatch Context，就不会因为收藏列表变化而重新渲染。
  • 把变化频繁的状态放在别处：如果一个值每秒变很多次（鼠标位置、输入框内容），不要放进 Context。
JSX
const FavoritesProvider = ({ children }) => {
  const [favorites, dispatch] = useReducer(favoritesReducer, undefined, loadFavorites);

  // 没有启用 React Compiler 时，手动稳定 value
  const value = useMemo(() => ({ favorites, dispatch }), [favorites]);

  return <FavoritesContext value={value}>{children}</FavoritesContext>;
};

什么时候用 Context

场景推荐做法
只隔了一两层直接传 props，清晰又简单
中间组件只是“摆放”子组件组件组合：把子组件作为 children 传进去（第 16 章）
主题、语言、当前登录用户Context：变化少、用的地方多
搜索词、筛选条件、分页URL（第 36 章）
从服务器获取的数据TanStack Query 等服务端状态库（第 40 章），它自带共享和缓存
复杂、频繁更新的全局客户端状态Zustand、Redux Toolkit 等状态管理库（第 45 章）
ⓘ Context 不是状态管理工具

Context 本身只是一个“传递机制”：它把一个值从上层送到下层，不负责存储和更新。 真正存状态的仍然是 Provider 里的 useState / useReducer。 理解这一点，就明白为什么大型应用会引入专门的状态管理库：它们在“存储”和“精确订阅”上做得更好。

小结

  • Context 解决“同一份数据要穿过很多层组件”的问题。
  • 推荐封装：一个文件里包含 Context（不导出）、Provider 组件、自定义 Hook（带 Provider 检查和业务方法）。
  • Context 值变化会让所有消费者重新渲染：按关注点拆分、稳定 value、拆分读写。
  • 不是所有共享状态都适合 Context：URL、服务端状态库、状态管理库各有更合适的场景。

面试题

Context 会带来什么性能问题？如何缓解？

Provider 的 value 变化时所有消费者都会重新渲染。可以拆分 Context、用 useMemo 稳定 value、分离 state 与 dispatch，并避免把高频变化的值放进 Context。

为什么要为 Context 封装一个自定义 Hook？

隐藏实现细节、提供统一的业务方法、在 Provider 缺失时给出清晰的错误，以及方便日后替换实现。

Context 是状态管理方案吗？

它是依赖注入 / 数据传递机制，状态仍由 useState 或 useReducer 管理；它没有选择性订阅能力，大型应用常配合或改用专门的状态管理库。

什么情况下不该用 Context？

只隔一两层（直接传 props）、可以用组件组合解决、数据应该放在 URL 中、属于服务端数据、或更新非常频繁时。
