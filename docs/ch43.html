可访问性

可访问性（accessibility，常缩写为 a11y）指让所有人都能使用你的应用：只用键盘的人、用读屏软件的视障用户、 色弱用户、手部不便的用户……这不是锦上添花：很多国家对公共网站有法律要求，而且可访问的应用对所有人都更好用， 测试也更容易写（第 30 章的 getByRole 靠的就是它）。

本章目标

  • 理解可访问性树，以及“语义化 HTML 优先”的原则
  • 保证键盘可用：Tab 顺序、焦点可见、焦点管理
  • 正确使用常见的 ARIA 属性，并知道什么时候不该用
  • 让异步更新（加载、结果数量）能被读屏软件播报
  • 用工具检查可访问性问题

读屏软件看到的是什么

浏览器除了 DOM 树，还会生成一棵可访问性树：每个节点有角色（按钮、链接、标题、列表……）、 名称（按钮上写的字、输入框的 label）和状态（是否禁用、是否展开、是否选中）。读屏软件读的就是这棵树。

第一原则：用对的 HTML 元素

❌ div 冒充按钮
JSX
<div className="button" onClick={handleRemove}>
  Dismiss
</div>
✅ 真正的按钮
JSX
<button type="button" onClick={handleRemove}>
  Dismiss
</button>
要做的事用这个元素
执行一个操作<button type="button">
跳转到另一个地址<a href> / <Link>（不要用 button + navigate 冒充链接）
页面结构<header>、<nav>、<main>、<footer>（读屏用户可以按区域跳转）
标题<h1>–<h6>，按层级使用，不要为了字号跳级
列表<ul> / <ol> + <li>（读屏会告诉用户“列表，20 项”）
表格数据<table> + <th>（第 33 章的排序列表其实更适合用表格）
弹窗<dialog>

每个控件都要有名字

JSX
{/* 输入框：label 关联（第 4 章的 htmlFor） */}
<label htmlFor="search">Search:</label>
<input id="search" />

{/* 只有图标的按钮：aria-label 提供名字（第 27 章） */}
<button type="button" aria-label="Dismiss story" onClick={…}>
  <Check width="18" height="18" aria-hidden="true" />
</button>

{/* 有意义的图片要有 alt；纯装饰的图片 alt="" */}
<img src={logo} alt="Hacker Stories" />
<img src={divider} alt="" />

第 16 章的 InputWithLabel 把 id 做成了 prop，原因之一正是：页面上有两个搜索框时 id 重复，label 就会关联错。 React 提供了 useId() 来生成唯一 id：

JSX
import { useId } from 'react';

const InputWithLabel = ({ children, ...props }) => {
  const id = useId(); // 每个实例唯一，服务端渲染时也一致

  return (
    <>
      <label htmlFor={id}>{children}</label>
      <input id={id} {...props} />
    </>
  );
};

键盘可用

  • 试试只用键盘：拔掉鼠标，用 Tab / Shift+Tab 移动、Enter / Space 激活，能不能完成搜索、删除、翻页？
  • 焦点要看得见：永远不要写 outline: none 而不提供替代样式。可以用 :focus-visible 只在键盘操作时显示焦点框。
  • Tab 顺序跟随 DOM 顺序：不要用 CSS 把元素视觉顺序打乱，也尽量不要写正数的 tabIndex。
CSS
button:focus-visible,
a:focus-visible,
input:focus-visible {
  outline: 3px solid #2b6cb0;
  outline-offset: 2px;
}

单页应用的焦点管理

传统网站换页时，浏览器会把焦点重置到页面顶部，读屏软件会读出新页面的标题。单页应用只是替换了一部分 DOM， 焦点可能停留在一个已经不存在的元素上，用户“迷路”了。这时需要用 ref（第 17 章）手动管理焦点：

路由切换后，把焦点移到新页面的标题上：

src/StoryPage.jsx
const StoryPage = () => {
  const story = useLoaderData();
  const headingRef = useRef(null);

  useEffect(() => {
    headingRef.current?.focus();
  }, [story.id]);

  return (
    <article>
      {/* tabIndex={-1}：可以被代码聚焦，但不会进入 Tab 顺序 */}
      <h2 ref={headingRef} tabIndex={-1}>
        {story.title}
      </h2>
      ...
    </article>
  );
};

弹窗：用原生 dialog

自己实现一个可访问的弹窗很难：打开时焦点要移进去、Tab 要困在弹窗里、Esc 要能关闭、关闭后焦点要回到触发按钮。 原生的 <dialog> 调用 showModal() 时，这些行为浏览器都已经做好了：

JSX
const ConfirmDialog = ({ open, onClose, onConfirm, children }) => {
  const dialogRef = useRef(null);

  useEffect(() => {
    const dialog = dialogRef.current;
    if (open) dialog.showModal();
    else dialog.close();
  }, [open]);

  return (
    <dialog ref={dialogRef} onClose={onClose}>
      <p>{children}</p>
      <button type="button" onClick={onClose}>Cancel</button>
      <button type="button" onClick={onConfirm}>Confirm</button>
    </dialog>
  );
};

ARIA：必要时的补充

★ ARIA 第一原则

能用原生 HTML 元素解决的，就不要用 ARIA。ARIA 只改变“读屏软件听到什么”，不会增加任何行为（键盘、焦点都要自己做）。 错误的 ARIA 比没有 ARIA 更糟糕。

属性用途本教程中的例子
aria-label给没有可见文字的元素一个名字图标按钮（第 27 章）
aria-hidden="true"对读屏软件隐藏纯装饰内容按钮里的 SVG 图标
aria-pressed切换按钮的开 / 关状态收藏按钮 ☆/★（第 37 章）
aria-sort表头当前的排序方向排序表头（第 33 章）
aria-invalid + aria-describedby标记出错的字段并关联错误信息表单校验（第 41 章）
aria-live / role="status"内容变化时主动播报加载状态、结果数量（下文）
aria-busy区域正在加载列表加载中

播报异步变化

用户点了 Submit，列表在后台更新了 —— 看得见的用户一目了然，读屏用户却什么也听不到。 把状态提示放在一个 live region 里，内容变化时读屏软件会自动读出来：

src/App.jsx
<p role="status">
  {stories.isLoading
    ? 'Loading stories…'
    : `${stories.data.length} stories found for “${query}”`}
</p>

<ul aria-busy={stories.isLoading}>
  ...
</ul>
ⓘ live region 要一开始就存在

读屏软件监听的是已存在的 live region 的内容变化。如果用 {isLoading && <p role="status">…} 条件渲染， 元素和内容同时出现，往往不会被播报。让容器一直渲染，只改变里面的文字。

小结

  • 读屏软件读的是可访问性树：角色、名称、状态。语义化 HTML 自动提供这些信息。
  • 优先用原生元素（button、a、label、dialog、ul、table），它们自带键盘和焦点行为。
  • 每个控件都要有名字：label、aria-label、alt；用 useId 生成唯一 id。
  • 单页应用要主动管理焦点：路由切换、删除元素、弹窗开关。
  • ARIA 只作补充；异步变化用 role="status" / aria-live 播报。
  • 用 jsx-a11y、axe、Lighthouse 和真实读屏软件检查。

面试题

为什么不应该用 div 加 onClick 实现按钮？

div 没有按钮角色，不能被 Tab 聚焦，也不响应回车和空格，读屏软件无法识别。需要手动补齐 role、tabIndex、键盘事件等，远不如直接使用 button。

ARIA 的第一原则是什么？

如果原生 HTML 元素或属性已经提供了所需的语义和行为，就使用原生元素，而不是用 ARIA 去改造其他元素。

单页应用中为什么需要焦点管理？

SPA 只替换部分 DOM，浏览器不会像整页跳转那样重置焦点；需要在路由切换、元素删除、弹窗开关等时机手动把焦点移到合理位置。

useId 有什么用？

为组件实例生成稳定且唯一的 id，常用于关联 label 与 input、aria-describedby 等，并在服务端渲染与客户端之间保持一致。

如何让读屏软件播报动态内容？

使用 aria-live 区域（如 role="status"），并确保区域元素一直存在，只更新其中的文字内容。
