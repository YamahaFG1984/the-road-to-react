性能优化

React 默认就很快，绝大多数应用根本不需要做性能优化。这一章的目的是理解： React 什么时候会重新渲染、哪些渲染是多余的、memo / useCallback / useMemo 各自解决什么问题 —— 以及 React 19 时代的 React Compiler 如何让你几乎不必手写这些。

本章目标

  • 理解 StrictMode 在开发环境下的双重执行
  • 让 effect 跳过首次渲染（以及这个技巧的局限）
  • 用 memo + useCallback 避免不必要的重新渲染
  • 用 useMemo 避免重复的昂贵计算
  • 了解并启用 React Compiler

先说 StrictMode

在请求数据的 effect 里加一行日志：

src/App.jsx
useEffect(() => {
  console.log('How many times do I log?');
  handleFetchStories();
}, [handleFetchStories]);

很多人以为只会打印一次，实际会打印两次 —— 连资深开发者都常被吓一跳。原因是 main.jsx 里的 <StrictMode>：从 React 18 起，它在开发环境下会把每个组件挂载 → 卸载 → 再挂载一次， 用来暴露缺少清理的 effect（第 14 章）。

对我们的数据请求来说，请求两次只是多了一个网络请求，结果一样（这种操作叫幂等的），不会造成 bug。 为了让本章的日志和生产环境一致，先暂时去掉 StrictMode，学完再加回来：

src/main.jsx
createRoot(document.getElementById('root')).render(<App />);

让 effect 跳过首次渲染

看看自定义 Hook useStorageState：

src/App.jsx
const useStorageState = (key, initialState) => {
  const [value, setValue] = useState(
    localStorage.getItem(key) ?? initialState
  );

  useEffect(() => {
    console.log('A');
    localStorage.setItem(key, value);
  }, [value, key]);

  return [value, setValue];
};

首次渲染时 effect 也会执行，把刚从 localStorage 读出来的值原样写回去 —— 这一次是多余的。 React 没有“只在更新时运行”的 Hook，但可以用 ref（第 17 章）记住“是否已经挂载过”，因为改 ref 不会触发渲染：

src/App.jsx
const useStorageState = (key, initialState) => {
  const isMounted = useRef(false);

  const [value, setValue] = useState(
    localStorage.getItem(key) ?? initialState
  );

  useEffect(() => {
    if (!isMounted.current) {
      isMounted.current = true;
    } else {
      console.log('A');
      localStorage.setItem(key, value);
    }
  }, [value, key]);

  return [value, setValue];
};
⚠ 这个技巧在 StrictMode 下会失效

StrictMode 模拟“卸载再挂载”时，ref 会被保留（仍然是 true），第二次挂载就不会被跳过。 这正说明它依赖了“effect 只会运行一次”这个不可靠的假设。本例中多写一次 localStorage 几乎没有成本， 所以现实中通常根本不需要这种优化 —— 把它当作理解 ref 的练习即可。

不需要的重新渲染

给 App 和 List 加上日志（List 用了一个小技巧：console.log() 返回 undefined，所以 || 右边总会执行）：

src/App.jsx
const App = () => {
  ...
  console.log('B:App');
  return ( ... );
};

const List = ({ list, onRemoveItem }) =>
  console.log('B:List') || (
    <ul>
      {list.map((item) => (
        <Item key={item.objectID} item={item} onRemoveItem={onRemoveItem} />
      ))}
    </ul>
  );
控制台输出
// 首次渲染
B:App
B:List
// 请求数据中，List 被 Loading 替换
B:App
// 数据到达
B:App
B:List

这些都合理。但在搜索框里打字时（还没点 Submit），每敲一个键都会输出：

控制台输出
B:App
B:List

List 收到的列表根本没变，却还是重新渲染了。这是 React 的默认行为：父组件重新渲染，所有子组件都跟着重新渲染， 不管 props 变没变。React 这样设计是因为“跳过渲染”判断错了会导致 bug，而重新渲染通常足够快。

memo：props 没变就跳过

用 memo 包裹组件，React 会在渲染前浅比较新旧 props，全都相同就跳过：

src/App.jsx
import { memo } from 'react';

const List = memo(
  ({ list, onRemoveItem }) =>
    console.log('B:List') || (
      <ul>
        {list.map((item) => (
          <Item key={item.objectID} item={item} onRemoveItem={onRemoveItem} />
        ))}
      </ul>
    )
);

再打字试试 —— B:List 还在打印！list 确实没变，但 onRemoveItem 变了： App 每次渲染都会创建一个新的 handleRemoveStory 函数（第 22 章讲过的“函数身份”问题）。

useCallback：让回调保持同一个引用

src/App.jsx
const handleRemoveStory = useCallback((item) => {
  dispatchStories({
    type: 'REMOVE_STORY',
    payload: item,
  });
}, []);

这个函数不依赖任何会变的值（要删的 item 是作为参数传进来的，dispatchStories 由 React 保证稳定），所以依赖数组为空， 只在首次渲染时创建一次。现在打字时只有 B:App，B:List 不再出现了。

ⓘ 什么是浅比较

React 用 Object.is 逐个比较 props：数字、字符串比较值；对象、数组、函数比较引用。 所以 <List style={{ color: 'red' }} /> 这样每次都写一个新对象字面量，也会让 memo 失效。

useMemo：避免重复的昂贵计算

假设标题要显示所有文章的评论总数：

src/App.jsx
const getSumComments = (stories) => {
  console.log('C');

  return stories.data.reduce(
    (result, value) => result + value.num_comments,
    0
  );
};

const App = () => {
  ...

  const sumComments = getSumComments(stories);

  return (
    <div>
      <h1>My Hacker Stories with {sumComments} comments.</h1>
      ...
    </div>
  );
};

函数放在组件外面，不会被重复创建；但计算本身每次渲染都会执行 —— 打字时每按一个键都输出 “C”。 这里的计算很便宜，但如果它要 500 毫秒，每次按键都会卡顿半秒。useMemo 缓存计算结果，只在依赖变化时重新计算：

src/App.jsx
import { useMemo } from 'react';

const sumComments = useMemo(
  () => getSumComments(stories),
  [stories]
);
API缓存的是什么典型用途
memo(Component)组件的渲染结果props 不变时跳过子组件渲染
useCallback(fn, deps)函数本身（引用）传给 memo 组件的回调；effect 依赖中的函数
useMemo(() => value, deps)函数的返回值昂贵的计算；需要保持引用稳定的对象/数组
★ 别过早优化

这三个工具都不应该“默认到处用”。比较 props、维护缓存本身也有成本，有时甚至比直接重新渲染还贵， 而且依赖数组写错还会引入 bug。先测量，确认真的有性能瓶颈，再有针对性地优化。 我们的应用没有任何性能问题 —— 学完这一节，建议把这些优化都删掉。

用工具测量

安装浏览器扩展 React Developer Tools。它会在开发者工具里增加两个面板： Components（查看组件树、props、state、Hooks）和 Profiler（录制一段交互，看每个组件渲染了几次、花了多久）。 在设置里勾选 “Highlight updates when components render”，页面上每次重新渲染的组件都会闪一下边框 —— 非常直观。第 42 章会详细介绍调试工具。

React Compiler：自动记忆化

手写 memo / useCallback / useMemo 很繁琐，也容易写错依赖。 React Compiler（2025 年 10 月发布稳定版 1.0）是一个构建时插件：它分析你的组件，自动在合适的地方插入等价的记忆化， 你照常写最朴素的代码就行。

小结

  • StrictMode 在开发环境下双重执行渲染和 effect，用于暴露问题；生产环境不会。
  • 父组件重新渲染会带动所有子组件重新渲染；memo 在 props 浅相等时跳过渲染。
  • 函数、对象 props 每次渲染都是新引用，需要 useCallback / useMemo 保持稳定，memo 才有效。
  • useMemo 缓存昂贵计算的结果。
  • 不要过早优化，先用 React DevTools Profiler 测量；React Compiler 可以自动完成大部分记忆化。

面试题

React 组件什么时候会重新渲染？

自身 state 变化、父组件重新渲染、或使用的 Context 值变化时。默认情况下，父组件渲染会导致所有子组件渲染，与 props 是否变化无关。

memo、useCallback、useMemo 分别做什么？

memo 在 props 浅相等时跳过组件渲染；useCallback 缓存函数引用；useMemo 缓存计算结果。

为什么只用 memo 有时不起作用？

如果父组件每次渲染都传入新的函数或对象（引用不同），浅比较会认为 props 变了。需要配合 useCallback / useMemo 或 React Compiler。

是否应该给所有组件都加上 memo？

不应该。比较 props 有成本，多数渲染很便宜。应先测量，只在确有瓶颈的地方优化。

React Compiler 是什么？

一个构建时工具，自动分析组件并插入记忆化逻辑，使开发者大多不必手写 memo、useCallback、useMemo；要求代码遵守 React 规则。
