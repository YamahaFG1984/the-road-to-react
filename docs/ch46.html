数据请求库选型

第 40 章用 TanStack Query 重写了数据层。但你还会听到 SWR、RTK Query、Apollo、tRPC、axios、ky…… 它们并不都是同一类东西。这一章把“数据请求”拆成几层，搞清楚每个库在哪一层，再比较同一层里的几个选择。

本章目标

  • 分清 HTTP 客户端、服务端状态缓存、API 类型三个层次
  • 比较 TanStack Query、SWR、RTK Query、Apollo Client
  • 了解如何让前端拿到后端 API 的类型（OpenAPI 生成、tRPC、GraphQL codegen）
  • 知道使用框架时，数据获取会发生什么变化

数据请求的三层

所以“TanStack Query 还是 axios？”是个伪问题 —— 它们不在同一层。第 40 章的 queryFn 里用的就是 axios。 真正需要比较的，是同一层里的几个候选。

第一层：HTTP 客户端

用了 TanStack Query 之后，重试、取消、错误状态它都会处理，HTTP 客户端的差别就不大了。 一个常见做法是用 fetch 自己封装一个十几行的小函数（统一加 baseURL、token、错误处理），既无依赖又够用：

src/http.js
const API_BASE = 'https://hn.algolia.com/api/v1';

const http = async (path, { params, ...options } = {}) => {
  const url = new URL(API_BASE + path);
  Object.entries(params ?? {}).forEach(([key, value]) =>
    url.searchParams.set(key, value)
  );

  const response = await fetch(url, options);

  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`);
  }

  return response.json();
};

// 用法
http('/search', { params: { query: 'react', page: 0 }, signal });

第三层：服务端状态库

先看同一个“获取搜索结果”的功能，在几个库里分别怎么写：

TanStack Query
JSX
import { useQuery } from '@tanstack/react-query';

const { data, isPending, error } = useQuery({
  queryKey: ['stories', query],
  queryFn: ({ signal }) =>
    http('/search', { params: { query }, signal }),
});
SWR
JSX
import useSWR from 'swr';

const { data, isLoading, error } = useSWR(
  ['/search', query],               // key
  ([path, query]) =>               // fetcher
    http(path, { params: { query } })
);
RTK Query（Redux Toolkit 自带）
JSX
import { createApi, fetchBaseQuery } from '@reduxjs/toolkit/query/react';

const hnApi = createApi({
  reducerPath: 'hnApi',
  baseQuery: fetchBaseQuery({
    baseUrl: 'https://hn.algolia.com/api/v1',
  }),
  endpoints: (build) => ({
    searchStories: build.query({
      query: (query) => `/search?query=${query}`,
    }),
  }),
});

// 自动生成的 Hook
export const { useSearchStoriesQuery } = hnApi;

const { data, isLoading } = useSearchStoriesQuery(query);
Apollo Client（GraphQL API）
JSX
import { gql, useQuery } from '@apollo/client';

const SEARCH_STORIES = gql`
  query SearchStories($query: String!) {
    stories(query: $query) {
      id
      title
      points
    }
  }
`;

const { data, loading, error } = useQuery(
  SEARCH_STORIES,
  { variables: { query } }
);
// （Hacker News 的这个 API 不是 GraphQL，仅作写法示意）

★ 选择建议
  • 没有特殊情况：TanStack Query。它不绑定框架（还有 Vue、Solid、Svelte 版本），生态和文档最好。
  • 已经用了 Redux Toolkit：用自带的 RTK Query，不必再引入一个库。
  • 后端是 GraphQL：Apollo Client 或更轻量的 urql；也可以 TanStack Query + graphql-request。
  • 只需要最基本的缓存和刷新：SWR。

第二层：让前端拿到 API 的类型

第 29 章我们手写了 Story 类型。手写的类型只是“我认为 API 会返回这个”，后端一改，前端并不知道。 更可靠的做法是让类型从后端自动来：

tRPC 的体验最接近“调用本地函数”，并且和 TanStack Query 深度集成：

TypeScript
// 服务端（Node / Next.js）
const appRouter = router({
  searchStories: publicProcedure
    .input(z.object({ query: z.string() }))
    .query(({ input }) => db.stories.search(input.query)),
});
export type AppRouter = typeof appRouter;

// 客户端：导入的只是类型，不会把后端代码打包进来
const trpc = useTRPC();
const { data } = useQuery(trpc.searchStories.queryOptions({ query }));
//      ^? data 的类型自动推导，参数写错会直接报错

使用框架时的变化

如果项目使用框架，数据获取的“主战场”会部分转移到路由和服务器：

环境首选的数据获取方式还需要 TanStack Query 吗
Vite SPA（本教程）组件内 useQuery需要
React Router 数据模式 / 框架模式路由 loader（第 36 章）可选：需要缓存、无限滚动、轮询时配合使用
Next.js App Router服务端组件里直接 await（第 51 章）可选：客户端交互多的部分（无限滚动、实时刷新）再用

小结

  • 数据请求分三层：HTTP 客户端（fetch / axios / ky）、类型（手写 / OpenAPI / tRPC / GraphQL codegen）、缓存（TanStack Query / SWR / RTK Query / Apollo）。
  • 不同层的库经常组合使用，只有同一层的库才需要比较。
  • 缓存层默认选 TanStack Query；已用 RTK 选 RTK Query；GraphQL 选 Apollo / urql；需求简单选 SWR。
  • 尽量让 API 类型从后端自动生成，而不是手写。
  • 使用框架时，首屏数据多由 loader 或服务端组件获取，客户端缓存库作为补充。

面试题

axios 和 TanStack Query 是什么关系？

不同层次：axios 是 HTTP 客户端，负责发送请求；TanStack Query 管理请求结果的缓存和状态，可以在 queryFn 里使用 axios 或 fetch。

SWR 和 TanStack Query 怎么选？

两者理念相同（stale-while-revalidate）。TanStack Query 功能更全（mutation、无限查询、DevTools 等）；SWR 更轻量，适合需求简单的场景。

什么是 tRPC？

一种在 TypeScript 全栈项目中实现端到端类型安全的方案：后端定义过程（procedure），前端通过导入类型直接获得参数和返回值类型，无需手写或生成 API 类型。

如何保证前端的 API 类型与后端一致？

从单一数据源生成类型：OpenAPI 规范生成、GraphQL schema codegen，或使用 tRPC 等共享类型的方案，避免手写类型与实际不符。
